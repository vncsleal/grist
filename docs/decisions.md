## Deferred

| Category | Planned Future | Hot-Swap Path | When |
|----------|---------------|---------------|------|
| Database (local) | libSQL (embedded SQLite) | `WorkspaceStorage` interface — swap `storage-fs` for `storage-db` in entrypoint. Zero tool changes. | When filesystem proves too slow for a user's data volume |
| Queue / Background jobs | Bull + Redis | `runGenerationJob()` is already an async fire-and-forget. Swapping to a queue = replace the runner, keep the job model. | When single-server processing isn't enough |
| Object storage (assets) | R2 / S3 | `saveHarvestOutput()` returns a path. Swap to signed URL generation at the storage layer. | When cloud mode needs cross-region asset access |
| Observability | Sentry + Prometheus | `slog()` already writes structured JSON to stderr. A log shipper can forward it. Prometheus exporter is a separate HTTP endpoint. | Post-v1, when users ask for it |
| SSO / OAuth | Google, GitHub login | better-auth supports it with `socialProviders` config. Add provider ID + secret, no code change. | Cloud v2 |
| Blob/image optimization | Cloudflare Images / Imgix | Media URLs are generated by providers. Frontend swaps the URL prefix. | When dashboard loads too slowly |
| Multi-region / edge | Cloudflare Workers | Hono runs on Workers unchanged. `apps/api` routes would need a CDN-friendly strategy. | When users are global |
| Admin audit log | Database table + portal UI | Add a `audit_log` table in Drizzle schema. Portal already has the admin routes slot. | Self-hosted v2 |

## Why Filesystem for LOCAL Mode

The question: why not use libSQL/SQLite for LOCAL mode instead of JSON files?

**Filesystem wins because:**

1. **Zero dependencies.** No database to install, no migrations to run, no server process. The MCP binary just works.
2. **Human-readable.** A copywriter can open `~/.quillby/workspaces/*/` and see their data as JSON files. They can back them up with `cp -r`, sync them with Dropbox, or edit them with any text editor.
3. **Single-user scale.** LOCAL mode serves one user. Even 10,000 cards across 10 workspaces is fast enough with JSON files. Node.js's `fs` is async and buffered.
4. **Simpler mental model.** "Everything is in `~/.quillby/`" is the entire architecture. No "what's my connection string?", no "did I run migrations?".
5. **The interface is the same.** `WorkspaceStorage` is the same interface whether backed by filesystem or libSQL. Switching later requires changing one line in the entrypoint.

**When to switch to SQLite:**
- If a user reports slowdowns with 50,000+ cards/drafts
- If multi-process access is needed (unlikely for LOCAL mode — one AI client at a time)
- If we need queryable data for LOCAL mode features (search, filtering)

**The hot-swap is trivial:**
```typescript
// main-local.ts — current (filesystem)
import { storage } from "@quillby/storage-fs";
const combinedStorage = storage as FullStorage;

// main-local.ts — future (libSQL)
import { getHostedUserStorage } from "@quillby/storage-db";
const combinedStorage = getHostedUserStorage("local-user") as FullStorage;
```

Everything else — all 11 tools, all resources, all prompts — works unchanged. This is already proven by the cloud entrypoint using `storage-db`.
